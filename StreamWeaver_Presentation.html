The Challenge

Big files crash naive ETL pipelines

Enterprise datasets arrive as gigabytes of CSV. Tools that buffer, parse eagerly, or run user code in-process simply collapse.

Problem
  • Memory blow-up: loading a 2 GB CSV into RAM is a non-starter; multi-GB files OOM servers.
  • Blocked UI: rendering 1,000,000 rows to the DOM freezes the browser.
  • Unsafe user code: running arbitrary uploader JavaScript in-process can hang or kill the pipeline.
  • Zero visibility: long runs show no progress; failures kill the whole job with no explanation.
  • No feedback loop: one bad row silently discards the dataset.
Solution
  • Stream everything: busboy upload → disk → parse → map → ingest; the file is never fully in RAM.
  • Virtualized grid: react-window renders only visible rows — 1,000-row preview scrolls with zero DOM lag.
  • Sandboxed transforms: user JS runs in an isolated context with a per-row timeout; a bad snippet marks the row, not the job.
  • Live progress: WebSocket broker streams rows/sec, counts, and status to the browser.
  • Batched, error-preserving ingest: 5,000-record bulkWrite flushes + a failed-rows report with reasons.

Memory audit: 0.81 GB in, 60.6 MB peak RSS

Full pipeline (parse → map → sandbox → batch) on a 10,000,000-row CSV while sampling process.memoryUsage().rss every 250 ms.

0.81 GBinput CSV processed
10,000,000rows streamed
60.6 MBpeak RSS (≤ 150 MB budget)
~79,800rows / second

Why memory stays flat

  • Every stage is a stream — nothing accumulates the file in memory.
  • The only persistent buffers are one 5,000-row batch + one failed-row batch.
  • Live heap after GC is ~5 MB regardless of input size.
  • Production server runs with a heap cap (--max-old-space-size=96) so V8 never lazily reserves past budget.

How we collected it

  • scripts/generateCsv.js — deterministic multi-GB CSV generator (quoted fields, numbers, booleans, dates).
  • scripts/memoryAudit.js — RSS sampler at 250 ms + full-pipeline metrics → tmp/audit-results.json.
  • Command:
    node --expose-gc --max-old-space-size=96 scripts/memoryAudit.js --file audit-live.csv --gc
  • withinBudget: true — recorded every run.

Technology Choices

Stack that matches the problem

Backend · Node.js 20+ / Express

  • busboy — true multipart streaming parser; the file is piped to disk, never buffered.
  • stream.Transform (objectMode) — CSV parse, mapping, sandbox, batch stages chain with backpressure.
  • isolated-vm / node:vm engine — sandboxed user transforms with per-row execution timeouts.
  • ws — WebSocket broker with per-job rooms and a 500 ms throttle.
  • MongoDB driver — insertMany(…, { ordered:false }) every 5,000 records; JSONL fallback for file-only demos.

Frontend · React (Vite)

  • react-window — virtualized CSV preview; only visible rows touch the DOM.
  • XHR upload — real upload percentage; pause/wring backpressure and cancel support.
  • Native WebSocket client with exponential-backoff reconnect.
  • Component set — Dropzone, VirtualGrid, MappingBoard, TransformEditor, ProgressBar, JobSummary, FailedRowsPanel.
  • Vite dev proxy — routes /api and /ws to the backend.
