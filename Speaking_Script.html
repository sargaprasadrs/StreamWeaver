Our project is a web application that moves large amounts of data — specifically, big CSV files — from one place to another, cleanly and reliably. To put it simply: a company uploads a data file, and StreamWeaver reads it, cleans it up, and stores it in a database. The interesting part is that we've built it to handle genuinely massive files without running out of memory — and I'll show you the proof shortly.

2. The problem

(Slow down a little here.)

Most data-processing tools have a simple flaw. They read an entire file into the computer's memory, process it, and then worry about the next one. That works fine for a small file — a thousand rows, no trouble. But when the file is two gigabytes — which in business data is completely normal — loading it all into memory is like trying to drink a lake. The server runs out of memory and quite literally crashes.

People usually solve this by buying a bigger server. We decided to solve it by building software that does not need a bigger server. That was the whole starting point.

There were also three smaller problems we wanted to fix:

First, viewing a million rows in a browser is slow, because the browser tries to draw all of them. Second, if you let users write their own simple code to transform data, that code needs to run safely so it can't crash the system. And third, when one row of data is bad, a normal tool quietly drops the entire file — and nobody knows which row caused it.

3. What we've built

(Keep it brisk — the detail lives in the demo.)

In four weeks, working in two-week chunks, we've built the full journey as a working application:

Week 1 — Upload and preview. Our backend receives the CSV using a streaming upload, which means the file is written to disk piece by piece as it arrives; it is never held in memory all at once. The frontend then shows a preview of the first thousand rows in a grid that only draws what's on screen, so even large files scroll smoothly.

Week 2 — The data pipeline. We built the processing core: reading the file incrementally, mapping columns to the target format, converting types like numbers and dates, and recording how the run went — all as a sequence of small, flowing steps rather than one big memory-hungry operation.

Week 3 — Safety and visibility. We added two things. First, users can write a small piece of JavaScript to transform rows, and it runs safely quarantined with a time limit, so a mistake can't hang or crash the server. Second, while a run is in progress, the live progress — how many rows done, how fast — streams to the browser in real time, so you're never left staring at an empty screen.

Week 4 — Saving results and handling errors. Records are written to the database in batches, and any row that fails is kept aside — with its row number and the reason — instead of stopping the whole run or silently disappearing. On screen, you get a summary of the run and a panel listing exactly which rows failed and why.

4. The evidence

(This is the part to land.)

We didn't want to just claim it works — so we built a small tester that creates a large CSV file and measures the server's memory while our code processes the entire thing.

What we testedResult
File size processed0.81 GB — roughly 10,000,000 rows
Peak memory used60.6 MB — our target ceiling was 150 MB
Processing speedabout 80,000 rows per second

To give you a sense, 60 megabytes is about the size of a small photo library. The file we fed it is roughly the size of a movie. Processing the movie-sized file while sitting comfortably inside the memory of a small photo library shows that the streaming design works exactly as intended.

We also keep a full automated test suite — 85 tests covering parsing, mapping, transformations, batching, and the API — and they all pass. A separate end-to-end test ran the whole flow: upload the file, map the columns, apply a transform, and read the results back. Everything came back correct.

5. Our plan for Week 1 — briefly

(Only include if asked about planning.)

For the record, we did follow a plan each week. In Week 1, for example, the schedule ran Monday to Sunday: scaffolding the project on Monday, the streaming upload on Tuesday, upload limits and cleanup on Wednesday, the preview sample endpoint and grid on Thursday, testing and grid polish on Friday, a full end-to-end run on Saturday, and documentation and the merge on Sunday. It's a simple rhythm — build, test, integrate — and it's held up every week since.

6. Status and what's next

So, where we stand: the application works end to end — upload, preview, mapping, safe transforms, live progress, batch storage, and failure reporting — and it's proven to stay well within memory limits even on a 0.81 gigabyte file.

Between now and the final review on October 19, we'll do three things: run the full two-gigabyte audit and freeze the numbers in the report, do a final end-to-end pass against every item in the specification, and lock everything into a clean release.
